# ADR B03b-001: Pure Scan V3 evidence contract and truthful legacy projection

Date: 2026-10-11 JST. Status: LOCAL_CANDIDATE; coordinator review required before runtime integration.
Base: 1963c469e2e3bd4819cda6bb9ef8162101ad523a.
Branch: codex/backend-program-20261011.

## Scope and existing behavior

This checkpoint owns two pure candidate modules and their unit tests. Existing v1 schemas, routes, providers, queue, client, storage and exports are unchanged. Current v1 requires positive estimated_quantity and a supported unit, only expresses VND price fields, defaults storage during schema parsing, and routes labels through the receipt path. These behaviors are not suitable as implicit defaults for incomplete V3 drafts.

## Contract decision

`ScanV3Schema` is a strict task-discriminated union with schemaVersion 3. The tasks are receipt_ocr, label_ocr and fridge_image_analysis. A document carries opaque documentId and sourceId. Each ordered item carries occurrenceId and sourcePosition. Duplicate occurrence IDs and decreasing source positions are rejected. Separate occurrences with identical contents remain separate, including when a source position describes a shared region. No content-based deduplication is performed.

Every extraction field explicitly carries either `{state:'known',value,basis,evidence}` or `{state:'unknown',reason}`. Unknown reasons are bounded. Known evidence must support its basis and bind to the same document and, for item source evidence, the same source position. Original source text is preserved, including whitespace. Source text spans and normalized image regions are validated. Missing fields, extra known values on unknown fields, unsupported bases and caller-declared status are rejected. Evidence structure is not a human review or dataset certificate.

Quantity separates amount, supported unit, purchase/package/observed basis and original source text. Positive finite amounts are required only when known. Physical purchased measures use g/kg/ml/l; purchase counts use count/package units. Package net content is never silently transformed into purchased amount. Model certainty and image-only observation cannot authorize a quantity projection. Conversion evidence requires an explicit reference, original source evidence and user-review reference; this module performs no food-specific conversion.

Money is `{amountMinor,currency:'VND'|'JPY'}`. Both supported currencies have zero decimal places; amounts must be nonnegative safe integers. Known money requires source extraction or user review. Unknown currency or amount is represented by an unknown whole money field. No FX conversion occurs. Receipt totals, unit prices, line totals, tax and discount are independent evidence fields; quantity times unit price is not forced to equal line total.

Labels have independent productionDate, expiryDate and netQuantity fields, and never require receipt merchant/totals. The legacy adapter rejects label task rather than borrowing a receipt DTO. Fridge items have no receipt money fields. Model-report basis is limited to confidence; confidence cannot become confirmed quantity or identity evidence.

Known canonical identity must cite exactly one matching certified-authority reference and cannot promote ING_ENR candidates. A supplied current-authority callback must confirm both release and canonical membership before a known identity can be projected. Missing, wrong-release, false or throwing callbacks fail closed. Unknown identity remains unknown and no name resolver is invoked.

## Readiness and public API

- `parseScanV3(input: unknown): ScanV3ParseResult` returns a parsed candidate or only SCAN_V3_INVALID_CONTRACT.
- `assessScanV3(input: unknown, authority?: ScanV3Authority): ScanV3Assessment` derives status and bounded reason codes.
- `scanV3ItemReadiness(item: ScanV3Item, authority?: ScanV3Authority): ScanV3ReadinessReason[]` inspects a parsed item.
- `projectScanV3ToLegacy(input: unknown, authority?: ScanV3Authority): ScanV3LegacyProjection` returns the task-tagged v1 suggestion or a typed incompatibility with the validated draft.
- `ScanV3Authority` is `{releaseId:string,hasCanonicalId:(canonicalId:string)=>boolean}` and is supplied from existing certified authority.
- Value/task/evidence/money/quantity schemas and inferred types are exported directly from the candidate module. Shared index exports are coordinator-owned.

SCHEMA_VALID means a valid envelope with no items. DRAFT means unresolved name, package-content quantity or receipt quantity not identified as a purchase. USABLE means names are usable for review while quantity evidence or known identity authority remains unresolved. CONFIRMABLE means pure field/quantity readiness only. Unknown canonical identity may remain absent in a legacy suggestion. CONFIRMABLE never authorizes an inventory command: B2 must still enforce authenticated human review, household/source proof, current authority, idempotency, quota and atomic status transition.

The adapter validates the constructed v1 payload but returns the input shape rather than legacy parsed output, preventing the legacy storage default from manufacturing a field. Unknown optional merchant/date/prices/confidence/category/storage/identity are omitted, never replaced by numeric zero, quantity one or a default unit. Required unknown name/quantity/unit/basis yields a typed unresolved draft. Any known JPY money anywhere on a receipt rejects the projection; it cannot populate a VND field. Legitimate repeated purchases retain quantity and price multiplicity. Projection does not mutate original extraction evidence.

## Error table

| Code | Pure function result | Future HTTP mapping proposal |
| --- | --- | --- |
| SCAN_V3_INVALID_CONTRACT | No raw payload or Zod issues | 422 malformed candidate |
| SCAN_V3_LEGACY_TASK_UNSUPPORTED | Valid label draft retained | 409 contract incompatibility |
| SCAN_V3_LEGACY_CURRENCY_UNSUPPORTED | Valid non-VND draft retained | 409 contract incompatibility |
| SCAN_V3_LEGACY_UNRESOLVED | Valid incomplete draft retained | 409 explicit review required |
| SCAN_V3_AUTHORITY_UNVERIFIED | Valid draft, known identity not trusted | 409 current authority review required |

Errors use bounded codes/reasons. The draft is intentional caller data for authorized review, not telemetry: callers must not log the entire result. No raw image, email, cookies, OCR text or Zod diagnostics are included in invalid-contract errors. Future HTTP integration must distinguish authorized draft response data from sanitized public error and metric metadata.

## Deferred B2 negotiation and rollout

Keep existing URLs. Opt-in through X-Scan-Contract-Version: 3; absent header remains v1. Reject unsupported versions with a stable documented error. Persist task and schema version in request/job/result/idempotency envelopes and bind fingerprints to task + contract version + body/image. Cross-version or cross-task key reuse returns 409 CONTRACT_IDEMPOTENCY_CONFLICT. This header/CORS/error/queue wiring is not implemented here.

Deploy version-aware readers before writers. New storage is expand-only and receives the next migration number from the coordinator; 0040 is already used by OTP. Legacy absent-version jobs/results remain v1. Rollback must read existing V3 history and preserve inventory/quota/event semantics. V3 drafts must never reach legacy quantity-one/unit-default confirmation fallbacks. Writer enablement requires client manual review readiness and separate storage/runtime/cancellation/budget evidence.

## Validation and completion

Focused adversarial tests cover UNKNOWN round trips, safe-integer VND/JPY money, malformed task/version/evidence, source provenance, duplicate occurrences, independent label task, truthful statuses, authority refusal and bounded errors. Scoped ESLint and strict TypeScript checks are required. Coordinator owns full local gates and independent review.

Passing local checks means CODE_COMPLETE_CONTRACT_CANDIDATE, not DATASET_CERTIFIED, PROVIDER_CERTIFIED, STAGING_CERTIFIED or PRODUCTION_APPROVED. No provider/network call, runtime writer, inventory mutation, data promotion or migration occurs here. Rollback is stopping use of the candidate modules; v1 bytes remain unchanged.
