# ADR-B01c-001 - Current membership and guest household authority

Status: ACCEPTED_FOR_LOCAL_IMPLEMENTATION. Base receipt 1963c469e2e3bd4819cda6bb9ef8162101ad523a.
Hosted certification remains separate. No schema or billing change is authorized here.

## Problem

Opaque sessions currently outlive household membership. Personalized recipe and
notification reads do not all carry a tenancy guard, while the default-household
guard recreates a missing membership. A revoked member can therefore regain or
continue household access. Cookie failure can also degrade to anonymous recipe
browsing instead of preserving the denied credential decision.

## Decision

Every protected request with an opaque cookie must resolve a live session and
current household membership in D1. A registered principal without membership
receives 403 TENANCY_VIOLATION before session touch or handler execution. A guest
cookie additionally requires that the household is still owned by that guest.
Missing/expired/revoked or malformed supplied cookies return 401 UNAUTHORIZED;
D1 absence or lookup failure returns 503 AUTH_UNAVAILABLE. A supplied cookie does
not fall through to development Bearer or anonymous recipe identity.

The tenancy guard remains a second current-membership check at household route
boundaries and never creates a household or membership as an authorization side
effect. Account/guest bootstrap keeps its existing creation authority. Existing
non-production signed-Bearer compatibility is retained; it cannot override a
supplied invalid cookie. This compatibility is not a production access method.

Recipe detail, recommendations and notifications receive explicit tenancy guards.
Anonymous recipe detail remains publicly readable with an empty inventory match;
it never reads the shared anonymous household sentinel from D1 or KV. Public
catalog content remains public. Household hard restrictions, inventory command
claims, planner creator privacy, cookies, expected-owner and CSRF remain intact.

No new family RBAC is introduced. Existing owner/member rows both authorize the
household operations already supported by the application. A dish MealRole is
unrelated to household roles. Requests admitted before a concurrent membership
revocation retain existing per-command SQL authorization; this entry check does
not claim a universal transaction spanning every read and response.

## Alternatives and consequences

Auto-restoring default membership treats a deliberate revoke as damaged bootstrap
state and is rejected. Checking only routes leaves unguarded personalized readers
and /me exposed; the cookie entry check protects all consumers. Denying every
anonymous recipe read would remove the established catalog browsing contract;
empty anonymous inventory preserves it without household data access.

The session lookup gains a bounded correlated membership EXISTS query using the
existing household/member indexes. The route guard remains useful for development
Bearer compatibility and for a fresh membership decision before household work.
No applied migration changes. Old sessions for revoked or deleted households stop
working and recovery requires an existing authorized bootstrap or membership flow,
not implicit recreation during a data request.

## Acceptance

SQLite-backed adversarial tests must first reproduce the gaps and then prove
403/no writes/no private response after default/nondefault membership removal or
household deletion, and guest foreign-household binding. Invalid cookies cannot
read anonymous sentinel stock or bypass owner fences. Valid owner/member/guest
operations and legacy Week/planner/inventory contracts retain their existing tests.
Fault injection fails closed with sanitized logs. Focused security tests, full
suite, lint, typecheck, migrations and sequential build must pass on the accepted
implementation. A rollback cannot restore the reproduced bypass.
