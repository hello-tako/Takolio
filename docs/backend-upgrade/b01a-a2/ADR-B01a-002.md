# ADR-B01a-002 - Strict OTP route, client and cleanup integration

Status: ACCEPTED_FOR_LOCAL_A2_IMPLEMENTATION.
This accepts the local design and API contract. It does not certify a final
committed tree, hosted D1, inbox delivery or production release. Final acceptance
requires the coordinator's source freeze and executed gates. It extends
[the dormant A1 ADR](../b01a/ADR-B01a-001.md); the applied
`migrations/0040_strict_otp_foundation.sql` remains byte-for-byte unchanged.

## Context and scope

A1 provided a dormant D1 authority. Existing routes still compared legacy OTPs,
and terminal issuance replay, registration creation, client recovery and cleanup
needed a single compatible cutover. A2 wires all OTP issue/verify/reset entry
points through the coordinator while retaining existing Origin, Turnstile,
password-login, cookie, owner-fence and rate-limiter checks.

Owned scope is the OTP repository/coordinator, an HTTP adapter, OTP portions of
`auth.ts`, request schemas, auth client/UI and receipt-aware cleanup with their
regression tests. Creating a pending registration principal also creates its
existing profile, household, owner membership, preferences, free subscription
and shopping list as one guarded transaction. Account ID and user ID are distinct.
The free-plan scan allowance comes from the unchanged scan-quota policy.

Non-goals are guest inventory transfer, Google OAuth redesign, billing/PayOS,
recipe/planner/inventory authority, new dependencies/config/workflows, provider
callbacks/reconciliation, secret rotation, remote migration, deployment, push or
real email/provider calls. Source review and local mocked delivery do not grant
operator approval for those actions.

## Authority and success effects

The account-wide request registry binds normalized email, purpose, operation and
semantic payload with keyed fingerprints. The budget remains account plus
purpose: five new candidate admissions in a rolling 900 seconds. A fifth admitted
candidate may finalize even though it establishes a 900-second lock against the
next candidate. Issuance cooldown is 60 seconds, challenge lifetime 600 seconds,
and comparison ticket deadline 30 seconds. Missing/pending/rejected/unknown/stale
challenge readiness still spends an admitted ticket; storage uncertainty never
permits comparison. No admission refund or retry-induced deadline extension exists.

Only the acknowledged reservation owner can compare. Finalization pins account
ID, user ID, normalized email, current generation, accepted/unconsumed issuance,
ticket deadline and target household membership. Required consume, activation,
password, session and outcome writes have same-batch assertions. Reset revocation
accepts zero or more old sessions and asserts none remain unrevoked before the new
session insert. Required zero writes or constraints abort the entire batch.
Lost responses are uncertain commits; persisted ownership prevents a second
comparison, duplicate session or repeated business effect on transport replay.

A fresh winning registration issuance creates required parent rows only when the
normalized account does not exist. An existing pending principal retains its
profile and password at issuance; repeated signup cannot replace those values.
A principal verified before reservation cannot be superseded by signup retry.
However, preserving a pending password alone permits preregistration takeover:
an attacker can know the password before the mailbox owner finishes activation.
Therefore registration verification requires the mailbox owner's chosen
`newPassword` and atomically installs it with activation, consume, session and
completion. Both registration and final reset enforce the existing 6..100 character
API bounds, and their verification fingerprints include the chosen password.

Final reset activates a pending account as well as preserving an already verified
account, because the OTP proves mailbox control. It replaces password/salt, revokes
old sessions and creates exactly one new session with consume and completion.
Preliminary reset records a fixed 900-second proof outcome only: no consume,
activation, password change or session. The ordinary client submits final reset
directly and does not add a preliminary admission.

## Route contract

Paths below are relative to the existing API prefix. Route schema validation and
existing middleware gates run before coordinator admission.

| Route / purpose | Coordinator operation | Result contract |
| --- | --- | --- |
| `POST /auth/register` | `issue_register` | Guarded pending principal plus issuance; accepted delivery 200; pending same-key replay 202; rejected/unknown delivery 503. No auth cookie. |
| `POST /auth/login`, pending account after password check | `issue_register` with login source/password fingerprint | Accepted issuance retains `requireOtp` with the existing 403 OTP-required response; pending 202 also includes `requireOtp`. Client enters verification and asks for the activation password. Verified password login keeps its existing session path. |
| `POST /auth/resend-otp`, register/login | `issue_register` / `issue_login` | Same issuance delivery contract; synthetic unknown account returns generic 200 without email dispatch. New explicit issuance requires durable cooldown and budget permission. |
| `POST /auth/forgot-password` and forgot resend | `issue_forgot` | Generic 200 for known/unknown new, pending, terminal and stale replay states; dispatch runs through scheduled background work. Response never claims delivered mail. |
| `POST /auth/verify-otp`, register | `register_verify` | Chosen `newPassword` required; atomic activation/password/session completion. Missing password is `VALIDATION_ERROR` 400 before admission. Guest transfer is the separate 409 decision below. |
| `POST /auth/verify-otp`, login | `login_verify` | Consumes accepted challenge and completes without creating a session. |
| `POST /auth/verify-otp`, forgot | `reset_preliminary` | Returns original proof/reset-flow token; no password or session effects. Extra `newPassword` is not forwarded by this route and cannot promote it to final reset. |
| `POST /auth/reset-password` | `reset_final` | Atomic chosen password, verified account, old-session revocation, fresh session, consume and completion. |

Known/unknown forgot issuance responses share message, status, delivery fields,
expiry and remaining cooldown metadata. Current pending/rejected/unknown delivery
and missing/expired/superseded/consumed/legacy challenges return generic
`OTP_INVALID` 400 for forgot candidates. D1 uncertainty remains protection-unavailable
503, and durable cooldown/budget remain 429 for both account classes. Synthetic
unknown authority consumes the same budget but can never activate, return a proof
or create a session. This is response/accounting parity; no timing indistinguishability
claim is made.

A candidate admitted before provider acceptance has a terminal readiness failure.
Later provider acceptance does not revive that ticket or permit a same-key compare.
The client retains the failed candidate key and never silently rotates it on
`OTP_INVALID`. Recovery requires an explicit new resend after the 60-second
issuance cooldown, creating a new generation and then a new verification request;
any active budget lock still applies. An issuance replay never resends email,
including accepted, rejected, unknown, pending, expired or superseded outcomes.

## Errors, metadata and credential replay

Coordinator responses expose `otpKeyIssuedAtMs` from the D1 epoch when available,
`otpExpiresAtMs` from the immutable issuance where relevant, and remaining
`retryAfterSeconds`. No fabricated server epoch is substituted when D1 fails.
429 cooldown/budget responses also set matching `Retry-After`. Codes are
`OTP_KEY_MALFORMED` 400, `OTP_KEY_EXPIRED` 410, `OTP_REQUEST_CONFLICT` 409,
`OTP_COOLDOWN`/`OTP_BUDGET_EXHAUSTED` 429, candidate `OTP_INVALID`/`OTP_STALE` 400,
register legacy `OTP_REISSUE_REQUIRED` 400, `OTP_IN_PROGRESS` 202,
`OTP_DELIVERY_UNAVAILABLE`/`OTP_DELIVERY_UNKNOWN` 503, and
`OTP_PROTECTION_UNAVAILABLE` 503 for uncertainty. Schema errors retain
`VALIDATION_ERROR` 400; an already verified signup retains
`EMAIL_ALREADY_REGISTERED` 409. Existing non-OTP middleware codes remain in force.

A first acknowledged register/reset completion may return its raw opaque session
only as an HttpOnly/Secure/SameSite cookie after a second query rechecks the exact
account/user/email, verified state, household membership, token hash, live expiry
and non-revocation. A failed lookup returns unavailable without a cookie even
when finalization already committed. Completion replay returns `sessionRequired:
true`, no raw token/user/cookie and no new session; the client returns to login.
Proof replay keeps the original expiry, cannot renew it and becomes stale after
principal change, consume, expiry or generation supersession.

## Client bootstrap and recovery

The first request without a server-clock receipt omits `Idempotency-Key`; the
server creates a fresh cryptographic key using D1 time. Every no-key retry is a
new operation/admission. This unavoidable bootstrap limitation is explicit.
After a response supplies D1 time, tab memory extrapolates it with monotonic elapsed
time and generates a 13-digit epoch-millisecond plus 32-lowercase-hex key. Keys
allow 1800-second age and 30-second future skew, rechecked inside reservation.

Tab-memory retry receipts bind route and normalized semantic body, exclude the
fresh Turnstile token, and reset on private-session/owner changes. Identical
transport retries preserve their key; changed code, password, operation or guest
choice uses a new request. Registration may prefill the activation password only
from its current in-memory submission. Direct links, refresh and unverified login
require a fresh chosen password. Credentials, code and retry keys are never
persisted in verify-context or local/session storage. Delivery presentation keeps
pending/unknown honest and uses response cooldown. Pending issuance 202 with
`requireOtp` enters the verification UI; it does not imply authenticated login.

Nonempty registration `migrateFromHouseholdId` returns
`INVENTORY_TRANSFER_DEFERRED` 409 before admission/comparison. Guest household,
inventory and membership remain intact. Explicit continuation without the field
uses the same OTP but a new semantic request, chosen password and separate account.

## Cutover and retention

Before marking retained unused legacy challenges used, lazy initialization imports
all retained failure/lock/cooldown evidence into strict scope accounting in the
same transaction. An assertion prevents ignored cutover/import writes from
committing partial state. Unprovable legacy challenges require reissue; digest
v1/v2 compatibility applies only to accepted strict issuance receipts.

Strict cleanup enforces a minimum 24-hour age and request-retention horizon. It
prunes tickets only after ticket/proof/request horizons and issuance expiry; then
unreferenced requests, then old expired issuances without request/ticket references.
It never deletes scope tombstones or imported accounting tickets. Expired legacy
rows with failures or lock evidence remain indefinitely until a separately
reviewed retention policy; only zero-failure/null-lock legacy rows can be pruned.
This conservative policy prevents cleanup/account recreation from refunding
active budget or erasing lazy-cutover evidence, at the cost of retained storage.
A current pointer may reference a pruned expired issuance; readers fail stale and
the next permitted issuance replaces it. No migration file is rewritten.

## Alternatives and trade-offs

| Alternative | Reason not selected for A2 |
| --- | --- |
| Continue route-local compare then increment | Concurrent reads can exceed the strict comparison bound; cannot repair after effects. |
| Retain preregistration password at activation | Mailbox owner can activate an attacker-known password. Chosen final password closes the takeover. |
| Wait for provider result in forgot response | Delivery state and response timing can expose account existence; generic scheduled work preserves the contract. |
| Automatically retry/refund readiness failure | Can spend fresh admissions or compare a previously terminal request without user intent; durable receipts remain irreversible. |
| Persist retry keys/passwords in browser storage | Extends credential lifetime and crosses owner/session boundaries. Tab memory accepts the bootstrap limitation. |
| Delete scopes/legacy failure rows aggressively | Erases abuse history and enables fresh-budget initialization; retain conservatively pending a new policy. |

The chosen design favors durable authority over automatic recovery. Users may
need explicit resend/login after readiness or lost-response outcomes, and normal
preliminary-plus-final clients would spend two admissions. Local tests do not
measure hosted D1 latency or guarantee email arrival.

## Dependencies, acceptance and next phases

A2 depends on additive migration 0040 from A1, the existing B01b typed delivery
adapter, existing cookie/Origin/Turnstile/owner guards, and the unchanged password,
OTP-digest and quota utilities. No new datastore or package is introduced.

Executed reviewer evidence is linked in [review-record.json](review-record.json).
The [transaction/parity focused run](../../../.artifacts/backend-b01a-a2/transaction-parity-final.log)
passed two files / 188 tests before the later DTO-fixture correction; its original
log remains intact. The [hardening correction run](../../../.artifacts/backend-b01a-a2/hardening-cooldown-final.log)
passed one file / 93 tests, including remaining cooldown on same-key replay.
The [client agent's final receipt](../../../.artifacts/backend-b01a-a2/client-register-password-receipt.json)
passed seven files / 128 tests, with the [independent helper review](../../../.artifacts/backend-b01a-a2/client-http-review.json)
recorded separately. These runs are not an aggregate final-head gate.

Final local acceptance requires source hashes matched to the final committed tree,
focused route/client/cleanup tests, full tests, lint/typecheck, local migration
replay and isolated local D1 schema/integrity checks, plus build and independent
review. Failed receipts must remain separate from passing reruns. Root owns these
remaining gates and the status/manifests; this ADR cannot mark them complete.

Before hosted rollout, prove strict admission/finalization and faults on controlled
staging D1, capture controlled inbox/provider evidence, review 0040-compatible
release/preflight readers and obtain a named hardened rollback version. Current
production/recovery scripts pinned to 0039 cannot certify 0040. B01c then broadens
auth/tenant adversarial coverage; B01b delivery certification/reconciliation remains
separate. Guest transfer requires its own authority/transaction ADR and tests.

OTP scope-HMAC secret rotation is an operational prerequisite decision: changing
the secret creates different account/scope hashes and can reset abuse authority.
Do not rotate until a reviewed preservation/overlap policy and staged proof exist.
Rollback must preserve expanded tables, requests, scopes, imports and outcomes,
continue strict admission with a compatible hardened reader, and never restore
unsafe legacy comparison or erase history to make rollback appear successful.
Production migration/deploy/provider operations require their separately authorized
release gate and are not performed by local A2 acceptance.
